# DATA SOURCES — Company Seed & Enrichment

## 0. 목표
- 회사명 + 홈페이지 URL을 가능한 많이 확보한다.
- 중복을 피하고, 소스별 정보를 병합한다.
- “정확도 100%”가 아니라 “운영 가능한 충분량”이 목표다.

## 1. OSM(OpenStreetMap) + Overpass API
### 1) OSM이란?
- 전 세계 지리 정보를 커뮤니티가 구축하는 오픈 지도 데이터.
- 점/선/면(POI 포함)에 태그가 붙는다.
- 예: `office=*`, `shop=*`, `name=*`, `website=*`, `addr:*` 등.

### 2) Overpass API란?
- OSM 데이터를 질의하는 API.
- 특정 지역 bounding box + 태그 조건으로 POI를 조회한다.
- 장점
  - 무료.
  - 지역 기반 수집이 쉬움.
- 단점
  - 한국 사업체 coverage가 소스/지역마다 들쭉날쭉.
  - 요청이 무거우면 timeout/504가 발생할 수 있음.

### 3) OSM 수집 설계
- region(서울/경기/대전/충청 등) 단위로 돌린다.
- mode(narrow/medium/wide)로 쿼리 폭을 조절한다.
- “잡음 제거”는 2단계로 한다.
  1) 쿼리 레벨에서 제외(예: office=government, shop=real_estate 등)
  2) 결과 레벨에서 키워드/태그 필터(동사무소, 행정복지센터, 부동산 등)

### 4) OSM에서 얻는 필드
- 회사명: `name`
- 홈페이지: `website` (없을 수 있음)
- 주소: `addr:*` 또는 `name+지역 역추정`
- 업종 힌트: `office=*`, `shop=*`, `craft=*`, `industrial=*` 등

## 2. SWDB (정보통신산업진흥원_SW산업정보종합시스템 사업자정보DB)
### 1) 데이터 성격
- SW 사업자 정보 목록(대량).
- CSV/ODcloud API로 제공.
- 확보량이 크다(수만 레벨 가능).

### 2) 컬럼(현장 파일 기준)
- 회사명
- 대표이사
- 홈페이지
- 본사주소
- 재무현황연도

### 3) 데이터 품질 이슈(자주 나옴)
- 홈페이지가 `http://`만 들어있음(실질적으로 빈 값).
- 이메일이 홈페이지 칸에 들어있음.
- `www.sunwooit.co.kr (수정중)` 같은 문구 혼합.
- 한 칸에 URL이 2개 이상(공백/줄바꿈/콤마로 분리됨).
- http/https 없이 도메인만 있는 경우(이건 살려야 함).

### 4) 권장 정제 정책(실무 기준)
- 입력값을 “가능한 살리고”, 사후에 dead 체크로 정리한다.
- 정제 규칙 예시
  - 문자열 strip.
  - `http://` 또는 `https://`만 단독이면 None 처리.
  - 이메일 형태면 None 처리.
  - 공백/콤마/줄바꿈으로 split 후 “첫 번째 유효 URL” 채택.
  - 괄호/‘수정중’ 같은 꼬리 문구 제거.
  - 스킴이 없으면 `https://` 붙여 저장.
  - 파싱 후 hostname이 없으면 None 처리.

> 실제 구현 위치:
- SWDB 레코드 파싱 구간(collect_swdb_companies 내부)
- 또는 공통 upsert 직전(홈페이지 정제 함수로 통일)

### 5) 재무현황연도(fin_year)의 해석
- 오래된 연도면 “업데이트가 오래된 회사”일 가능성이 높다.
- 홈페이지가 죽어있을 확률이 증가한다.
- 대응
  - 일단 수집은 한다(회사명은 가치가 있음).
  - 홈페이지 dead 체크에서 자연스럽게 `dead`로 정리한다.
  - 운영상 `dead`는 재체크 스킵 옵션으로 비용 절감한다.

## 3. DART(OpenDART, 금융감독원)
### 1) 데이터 성격
- 공시 기반 기업 정보.
- coverage는 “공시 대상” 위주라 일반 소상공인/영세업체는 적다.
- 대신 신뢰도 높고 상장사/규모 있는 회사 비중이 높다.

### 2) 왜 신규 생성은 “상장사만”?
- DART 전체 기업을 신규 생성하면 “지역/업종” 목적과 어긋날 수 있음(대상 범위 과확장).
- 상장사는 취업 선호도가 높고, IT 포지션 채용도 빈번하다.
- 따라서 정책:
  - `stock_code` 있는 기업만 신규 생성.
  - 기존 Company는 corp_code/주소/연락처/IR URL 등 보강.

### 3) DART에서 얻는 필드
- corp_code (고유 식별)
- stock_code (상장사 여부)
- 주소/연락처/팩스
- 홈페이지(hm_url)
- IR URL
- 산업코드/분류 힌트
- 설립일(est_dt, 보통 YYYYMMDD)

### 4) 운영 주기 추천
- “변경분 중심”으로 주 1회면 충분.
- 이유
  - 공시 시스템은 이벤트 기반 업데이트.
  - 매일 돌릴 실익이 크지 않음.
- 보통 `since_days=14` 정도로 주간 변경분만 처리.

## 4. 중복 방지(멀티 소스 병합) 정책
### 우선순위
1) dart_corp_code
2) homepage_host(도메인)
3) name_norm(정규화 회사명)
4) name(원문)

### source_meta(JSON) 사용 목적
- 소스별 원천 데이터를 충돌 없이 축적.
- 예:
  - `source_meta["swdb"]["fin_year"]`
  - `source_meta["dart"]["corp_cls"]` 등

## 5. dead(홈페이지 생존) 체크 운영 전략
### 1) 왜 필요한가?
- SWDB/OSM은 홈페이지가 죽어있거나 더러운 경우가 흔하다.
- “수집 시 정제만으로 완벽 해결”이 어렵다.
- 따라서 “수집은 넓게, 생존 체크로 후처리”가 운영 비용 대비 효율이 좋다.

### 2) 비용/성능 관점
- 전체 3만+ 홈페이지를 노트북에서 한 번에 체크하면 오래 걸릴 수 있다.
- 권장 운영
  - 노트북: limit=20~30으로 테스트만.
  - 운영 PC: 야간에 전체 실행(또는 배치로 나눠 실행).
  - 이미 dead인 것은 skip 옵션으로 재검사 비용 절감.

### 3) 권장 정책 예시
- 최초 1회(운영 PC): 전체 실행
- 이후 연 1회: 전체 재검사(또는 최근 1년 미체크 대상만)
- dead는 1년마다만 재검사(또는 skip_dead=True 유지)
